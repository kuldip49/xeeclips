# Online provider connectors

ONLINE uses only the enabled OpenAI adapter with model `gpt-5.6-luna`. Google, NVIDIA, Anthropic, Groq, and OpenRouter remain registered but are disabled from the active ONLINE pool. Luna failure follows the existing deterministic fallback behavior; there is no cross-provider failover. OFFLINE uses the existing Ollama path only. FALLBACK_ONLY makes no LLM calls.

`ONLINE_PROVIDER_ORDER` is kept as a compatibility setting and defaults to `openai`; ONLINE role-specific provider overrides are ignored so every ONLINE role uses OpenAI Luna. Unknown, disabled, unsupported, or unconfigured providers are skipped. `*_ENABLED`, `*_MODEL`, `*_<ROLE>_MODEL`, `*_CONCURRENCY`, `*_BASE_URL`, and `*_API_KEY` configure each adapter. Existing Google/NVIDIA connector settings remain supported outside the active ONLINE pool.

`GET /ai-providers` returns safe config metadata and provider state. `PATCH /ai-providers/:id` accepts `enabled`, `priority`, `model`, `modelsByRole`, `capabilities`, and `concurrency`. `POST /ai-providers/reorder` accepts `{ "providerIds": ["google", "nvidia", "openai"] }`. `POST /ai-providers/:id/test` sends a small JSON request and returns connectivity, model availability, latency, and a normalized failure category. The API never accepts or returns keys. Add keys through environment variables. Runtime PATCH/reorder changes are held in memory and reset on backend restart; they are not stored in Prisma. This avoids putting secrets in a plaintext config table. A future persistent settings implementation can store only non-sensitive overrides and fetch credentials from a separate encrypted secret store.

Routing calls each eligible provider at most once. Auth and missing-model failures mark that provider/model unavailable until configuration changes or health is reset; quota failures use `LLM_QUOTA_COOLDOWN_MS`. Rate limits respect `Retry-After`; 503 saturation cools down the role briefly. Timeouts, ordinary 5xx failures, and schema or truncated output failures do not disable unrelated roles. A successful provider can re-enter the pool after its cooldown. The provider request service applies per-provider/model concurrency and preserves role-specific token budgets. Cloud enrichment failures continue through the existing deterministic pipeline fallbacks.

To add a provider, implement `LlmProviderAdapter` in `provider-registry.ts` (or a separate adapter file), register it in `ProviderRegistry`, supply its endpoint/configuration and capabilities, add its vendor request style to `LlmProviderService` if needed, then configure its key, model, and enabled/order settings. No video-processing service changes are needed.

Rebuild: `npm --workspace apps/backend run build`. Run the connector fixtures: `npm --workspace apps/backend run test:provider-connectors`. Run mode and routing regressions: `npm --workspace apps/backend run test:ai-modes` and `npm --workspace apps/backend run test:multi-model`. With a backend server running, test a configured connector with `POST http://localhost:4000/ai-providers/google/test`. Run the synthetic live check with `npm --workspace apps/backend run verify:online-live`.
