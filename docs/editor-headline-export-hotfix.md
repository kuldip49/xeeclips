2. **Why INVALID_TIMELINE was emitted.** `EditModeRenderService.run` called `validateRenderPlan`, built ASS, detected the headline in `ass.overflowed`, and threw `EditExportError('INVALID_TIMELINE', ...)`. The timing error enum was reused for typography. That branch now calls `validateHeadlineFit`, which returns `HEADLINE_DOES_NOT_FIT` and: “Headline is too large for this layout. Reduce the size, enlarge the text box, or shorten the text.” The frontend exposes the same warning before export.

   Validation order remains: load the exact committed revision; load/probe source and assets; build the canonical timeline, camera and overlays; validate video trims, timeline ranges, canvas, overlay structure and audio; compile text layout/ASS and validate headline fit; render with FFmpeg; probe and run media QA; save the export with its source revision. Fit cannot bypass genuine timeline validation.

3. **Was the timeline actually invalid?** No. `validateRenderPlan` passed both captured states, with no zero/negative range or out-of-bounds overlay. Genuine invalid VIDEO trims still return `INVALID_TIMELINE` in the focused and real-media suites.

Browser/libass rasterization, shadows and rounded plates retain existing documented differences; this change establishes headline fit and wrapping parity, not pixel identity for the whole video composition.
